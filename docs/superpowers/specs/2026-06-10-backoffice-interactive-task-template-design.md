# 后台管理类网站交互式任务模板设计

生成时间：2026-06-10

## 1. 背景

截至 `2026-06-10`，FlowWeave 当前主线已经完成 P2 收口：

1. 扩展录制、知识库同步、Studio / Web 回放主链路已打通。
2. 当前能力更擅长“录一次具体操作，再按同一路径重放”。
3. `variables[]`、模板插值、Studio 运行前变量输入已经存在，但仍停留在“Flow 级统一收集变量”的窄闭环。
4. 真实后台高频场景中的“每次业务数据不同，但主路径稳定”还没有被正式定义为产品能力。

用户描述的“新建酒店 -> 输入本次数据 -> 搜索刚创建实体 -> 进入详情继续操作”不是单一酒店场景问题，而是后台管理类网站中的通用任务结构：

- 创建或修改一个业务实体
- 填写本次运行才知道的数据
- 搜索并定位目标实体
- 切换到目标上下文
- 继续完成后续重复步骤

这意味着下一大版本的核心问题已经不是“能否录下来”，而是：

**能否把已录制流程编辑成一个可重复执行、可在关键节点收集输入、能稳定完成后台任务的模板。**

## 2. 产品定义

### 2.1 一句话定义

FlowWeave vNext 不是“更强的录制器”，而是一个面向后台管理类网站的**交互式任务模板工作台**：先录制真实流程，再在 Studio 中把它编辑成可在关键节点收集输入、并能稳定反复执行的模板。

### 2.2 产品单位

下一大版本的核心单位不是单个步骤、变量或弹窗，而是：

- **任务模板**

其中：

- 录制步骤：模板的执行骨架
- 输入节点：模板中显式定义的运行时收集点
- 变量绑定：模板把输入与后续步骤连接起来的机制
- 执行实例：模板在某次具体运行中的一次带参执行

## 3. 目标用户与边界

### 3.1 核心用户

第一版主用户先定义为：

- **录制者自己反复执行**

典型用户包括：

- 后台运营
- 实施与交付人员
- 测试与验收人员
- 内部管理系统的高频操作者

产品结构上要为未来“录制者创建、同事执行”留空间，但**不把协作作为第一版重点**。

### 3.2 目标网站类型

下一大版本先聚焦：

- 后台管理类网站
- B 端运营台
- CRM / ERP / PMS / 电商后台
- 以表单、搜索、列表、详情页、筛选区为主要结构的网站

明确不以“任意网站自动化”作为第一版目标。

### 3.3 目标任务类型

第一版优先覆盖以下三类后台任务：

1. 表单填写
2. 筛选 / 查询
3. 搜索后选择实体，并进入后续工作上下文

## 4. 方案比较

### 方案 A：继续增强录制器

做法：

- 继续扩大录制覆盖率
- 增加更多动作类型
- 保持“录完即重放”为主模型

优点：

- 改动最小
- 延续当前心智

缺点：

- 不能解决“每次输入不同”的核心问题
- 不能把录制产物变成长期可复用模板
- 仍然会被具体业务数据绑死

### 方案 B：统一运行前大表单

做法：

- 不改流程结构
- 所有变量都在运行前一次性填写

优点：

- 执行链简单
- 比当前版本更容易复用

缺点：

- 无法表达“执行到某一步再输入”
- 不适合长流程、分阶段决策流程
- 会把不同上下文的数据收集全压成一张大表单

### 方案 C：交互式任务模板（推荐）

做法：

- 先录制真实流程
- 在 Studio 中显式加入输入节点
- 后续步骤行内绑定变量
- 运行到输入节点时再暂停收集、继续执行

优点：

- 贴近后台管理类任务的真实结构
- 能兼容“一次性收集”和“分段收集”
- 能让 Studio 成为模板编辑与执行中心
- 比通用编排器更克制，比纯录制器更有业务价值

缺点：

- 执行协议需要从“单次跑完整个流程”升级为“可暂停 / 继续的会话”
- DSL、Studio、Runtime 都需要新增一层产品模型

### 推荐结论

采用 **方案 C：交互式任务模板**。

## 5. vNext 第一版目标

### 5.1 核心目标

1. 让录制流程可以在 Studio 中被编辑成模板，而不只是原样重放。
2. 允许作者在流程中显式插入输入节点，并定义这一段流程运行时需要收集哪些字段。
3. 允许后续录制步骤把原始字面值改成变量绑定。
4. 支持后台高频的“搜索后选择实体”模式，但先以原始步骤组合完成，而不是先大量引入高级复合节点。
5. 运行时走到输入节点才暂停，并由 Studio 收集输入后继续执行。

### 5.2 成功标准

1. 作者可以把一条已录制流程编辑成可重复运行的模板。
2. 同一模板既支持：
   - 开头一次性收集整组输入
   - 中途分段收集输入
3. 模板变量不仅可用于填值，也可覆盖第一版允许的动态定位/跳转位置。
4. Studio 能清楚表达变量来源、变量消费位置、暂停原因与继续位置。
5. 不引入条件分支、循环、多人协作等超范围能力。

## 6. 第一版功能范围

### 6.1 模板编辑

Studio 第一版提供：

1. 录制步骤顺序视图
2. 显式输入节点插入能力
3. 行内变量绑定
4. 运行预览

第一版不要求先做可视化流程画布；**顺序步骤流**就是主编辑界面。

### 6.2 输入节点

产品层统一术语使用：

- **输入节点**

说明：

- 它表示“运行到这里时，需要由用户补充信息”
- 它的呈现方式可以是 Studio 弹窗或侧边输入面板
- 不建议在产品里使用“弹窗节点”作为主术语，以避免与网页自身 modal 混淆

输入节点具备以下产品属性：

1. 节点名称
2. 节点说明
3. 字段列表
4. 字段类型（至少支持 string / number / boolean）
5. 字段是否必填
6. 默认值（可选）

第一版不要求：

- secret 字段托管
- 动态表达式字段
- 多层变量域

### 6.3 变量绑定

第一版变量绑定采用：

- **原始录制步骤上的行内绑定**

也就是说，当前步骤原本的某个字面值，可以改成引用输入节点里的字段。

第一版优先开放的绑定面：

1. `fill.value`
2. `select.values[]`
3. `navigate.url`
4. `wait.urlIncludes`
5. 受控的 `role.name` / `text`

第一版不鼓励在 UI 中开放：

- 任意 CSS / XPath 变量化

原因：

- 过早开放底层定位器变量化，会让模板看起来灵活，但稳定性和可诊断性显著变差

### 6.4 搜索后选择实体

第一版必须支持后台高频的“搜索后选择实体”任务，但先按**原始步骤组合**来做，不先抽象高级业务节点。

推荐表达方式：

1. 搜索输入步骤绑定变量
2. 等待结果更新
3. 选择步骤继续使用原始 click / press / wait 组合

Studio 必须把这两层依赖分开表达：

- 搜索步骤绑定了哪个变量
- 选择步骤依赖的是哪个搜索结果上下文

如果某个“选择步骤”仍然只是录制时命中的那一条静态结果，Studio 需要明确提示：

- 这一步还没有真正完成参数化

### 6.5 运行时交互

第一版运行态必须支持：

1. 执行到输入节点时暂停
2. 弹出输入界面
3. 填写后继续从当前节点后执行
4. 在执行界面中清楚展示：
   - 当前执行到哪一步
   - 为什么暂停
   - 这次已经收集了哪些输入
   - 提交后将从哪里继续

## 7. UX 设计原则

### 7.1 编辑态

编辑态优先遵循：

- **步骤中心 + 显式输入节点 + 行内绑定**

关键交互对象应包括：

1. 步骤流 / 节点列表
2. 输入节点卡片
3. 变量面板
4. 行内绑定入口
5. 步骤详情面板
6. 变量来源 / 消费提示

### 7.2 运行态

运行态至少需要：

1. 执行进度轨
2. 输入收集弹窗 / 输入面板
3. 暂停状态条
4. 本次运行上下文摘要
5. 明确的“提交并继续”动作

### 7.3 UX 风险控制

第一版必须重点避免：

1. 用户把“输入节点”误解成网页里的弹窗
2. 用户以为改了搜索词，后面的选择步骤就自动跟着变
3. 用户搞不清楚流程暂停后是“从头再跑”还是“从当前节点继续”

## 8. 第一版边界

### 8.1 明确支持

1. Studio Desktop
2. 单人使用
3. 线性流程
4. 显式输入节点
5. 有限变量绑定
6. 表单填写 / 筛选查询 / 搜索后选择实体

### 8.2 明确不做

第一版不做：

1. 条件分支
2. 循环
3. 子流程
4. 批量数据集执行
5. 多人协作、模板分发、审批权限
6. 自动从录制里抽变量
7. AI 改流程、AI 推荐变量
8. 通用开放式 DSL
9. 任意站点通吃
10. 关闭 Studio 后从中断节点恢复长会话

## 9. 术语约定

建议产品内统一使用以下术语：

- 任务模板：用户保存和复用的核心资产
- 录制步骤：从浏览器录制得到的原始动作
- 输入节点：运行时收集信息的显式节点
- 变量绑定：把后续步骤字段连接到输入值
- 执行实例：模板在某次输入下的一次运行

不建议作为主术语使用：

- 弹窗节点
- 智能节点
- AI 节点

## 10. 风险与约束

### 10.1 产品风险

1. 如果第一版边界不够硬，产品会滑向通用编排器。
2. 如果变量开放面过宽，模板会从“可复用”滑向“脆弱但看起来灵活”。
3. 如果搜索步骤和选择步骤的关系表达不清，用户会误判模板已经完成参数化。

### 10.2 技术约束

1. 现有 runtime 是单次执行模型，下一版要升级为会话式暂停/继续协议。
2. 现有 Studio 变量输入仍是 Flow 级统一表单，尚无步骤级输入节点模型。
3. 当前执行上下文中的变量值并不适合被描述为“安全托管”或“敏感信息已受保护”。

## 11. 下一步设计拆解

在进入实现计划之前，下一轮设计必须把以下三件事单独定死：

1. 输入节点的数据结构
2. Studio 的模板编辑模型
3. Runtime / Electron 的暂停继续会话协议

这三件事定清后，才能进入实现层规划。

## 12. 综合结论

FlowWeave 下一大版本应从“录制回放工具”升级为“后台管理类网站的交互式任务模板工作台”。

第一版必须坚持以下收敛：

- Studio-only
- 线性流程
- 显式输入节点
- 行内变量绑定
- 表单 / 查询 / 搜索后选择三类高频后台任务

这样既能承接当前产品基础，又能避免过早走向过宽的通用编排器。
